# SMS UI Build Progress

Tracking implementation of the full school-ERP feature spec on top of the existing React 19 + TS + Vite + shadcn/Radix + TanStack Query + zustand stack. UI-only — every module fakes a backend via localStorage + mockDelay, same convention as the original 7 modules (students, staff, administration, authentication, dashboard, parent-portal).

Updated `reports/api.ts`'s `getAdmissionsReport()` and `reports/components/AdmissionsTab.tsx` to group by the new `stage` field instead of the removed `status`, with "approval rate" now meaning enrollment rate (enrolled ÷ total). Full pipeline walked end-to-end live in-browser (inquiry → registration → entrance exam → interview → decision → fee payment → enroll, plus waitlist-promote and the reject/withdraw confirm dialogs) with no console errors.

19. **Payroll & HR** (`src/features/payroll/`) — the second Phase B sub-module (user's choice again). "HR" itself turned out to already be thoroughly covered by the pre-existing Staff Management module (qualifications, experience, documents, performance reviews, promotions, resignation, and leave requests all predate this task), and per-employee salary structure + a bare one-click-at-a-time "record this month's payment" log already existed too (`StaffMember.salary`/`salaryHistory`, `staff/components/profile/SalaryTab.tsx`). So this task's real scope was the genuinely missing piece: an actual **Payroll** system — bulk monthly runs and itemized payslips — built as a layer on top of that existing per-staff data rather than a parallel, disconnected one (learned from the task-17 follow-up about `authentication/mockUsers.ts` vs. `administration/users/mock.ts` being two silently-disconnected datasets that happen to share names — didn't want to repeat that mistake here). **Payroll Runs**: `generatePayrollRun(month)` bulk-creates a draft `Payslip` (snapshotting each eligible active/on-leave staff member's *current* `salary` structure) for every one of them who doesn't already have a `salaryHistory` entry for that month — staff already paid outside the payroll flow (or in an earlier run) are silently skipped, and re-generating the same month is rejected outright. `finalizePayrollRun` locks a run in (mirrors Accounting's draft→posted pattern); a finalized run can no longer be deleted, which here isn't just an integrity nicety but a real cross-module safety concern — a paid payslip has already written a `salaryHistory` entry on the real staff record via `recordSalaryPayment`, so deleting the run out from under it would silently orphan that record. **Payslips**: a filterable (by month/status) list across every run, each with a print-style itemized `PayslipView` (basic/allowances/deductions/net pay/bank details, mirroring Fees' `ReceiptView`), and a "Mark paid" action that both flips the payslip and calls the *real* `recordSalaryPayment(staffId, month)` so the staff member's own Salary tab reflects it immediately — verified live end-to-end (marked Daniel Reyes's August payslip paid from Payroll, confirmed it appeared in his own staff profile's payment history within the same check). Seeded three historical runs built by joining the *live* `listStaff()` roster (not the static seed constants) against whatever `salaryHistory` entries already existed, so the numbers never contradict what a staff profile already shows; the school's staff roster had actually grown to 17 people by this point in the build (new Drivers/Wardens/Teachers seeded by the Transport/Hostel/Teachers modules), several with no salary ever configured (₹0 basic/allowances/deductions) — the payroll run correctly surfaces these as ₹0 payslips rather than silently excluding them, which is arguably more useful (it's a visible data-quality flag: "this employee has no salary on file") than hiding the gap. Full generate → finalize → duplicate-rejected → mark-paid workflow verified live for a real September 2026 run. Route: `/payroll`, nested under the existing "Human Resources" nav section alongside Staff Management, gated by a new `payroll` permission added to `ADMIN_ONLY_MODULES`.
20. **Inventory Management** (`src/features/inventory/`) — the third Phase B sub-module (user's choice again), and the first one with no pre-existing partial implementation anywhere else in the app to build on — a genuinely standalone module. Modeled as a real perpetual-inventory system rather than a flat item list: **Items** carry a `quantityInStock` that can *only* change through a stock transaction, never a direct edit (`updateItem` deliberately excludes it from `InventoryItemFormValues` — new items always start at zero and get their opening stock through a purchase, the same discipline Library enforces on `Book.availableCopies`). **Stock Transactions** are the append-only audit trail: `recordPurchase` (stock in, optional vendor + unit cost, updates the item's cost to the latest purchase price), `recordIssue` (stock out to a department/class, server-side-*and*-client-side blocked — via the number input's `max` attribute *and* a matching `api.ts` check — from taking out more than is on hand), and `recordAdjustment` (set a freshly-counted quantity after a physical stock take, with a live "+N/-N relative to current stock" delta preview before it's saved). **Reports** aggregates low-stock items (at or below `reorderLevel`, sorted by how short they are) and stock valuation by category, both pure derivations over the live item list with no separate stored report data. Seeded 18 items across 6 categories (Stationery/Sports/Lab/Furniture/Electronics & IT/Cleaning), 5 vendors, and ~26 transactions (opening purchases + issues + one stock-take adjustment) computed so that 6 of the 18 items land at or below their reorder level — a deliberately realistic mix rather than an all-healthy or all-empty catalog, so the low-stock report has something to show on first load. Full stock-in → issue (including a rejected over-issue) → adjustment cycle verified live, with the item catalog and valuation numbers updating correctly after each one. Route: `/inventory`, its own new "Inventory" nav section (mirroring the one-section-per-standalone-module pattern used by Library/Transport/Hostel), gated by a new `inventory` permission added to `ADMIN_ONLY_MODULES`.
21. **Certificate Generator** (`src/features/certificates/`) — the fourth Phase B sub-module (user's choice again). Six certificate types (Bonafide, Transfer, Character, Study, Achievement — all student-facing — plus Staff Service Certificate) generated from a single unified form (`GenerateCertificateTab.tsx`, a full page like Communication's `ComposeTab`, not a dialog) whose one zod schema uses `superRefine` to make different fields required depending on the selected type, rather than building six separate forms. Every generator function reads the recipient's **real** record via the owning module's own `api.ts` (`listStudents()`/`listStaff()`) rather than re-collecting data already on file: the **Transfer Certificate** is the sharpest example — it reuses the student's real `transferRecord` (already captured by the Students module's own "Transfer student" action) for the destination school/reason/date, and issues the certificate under that record's *actual* `transferCertificateNumber` rather than minting a new one, so the number a school already promised a leaving student stays consistent everywhere it appears. It throws a clear error (surfaced as a toast) if a student without a transfer record is selected for a Transfer Certificate, rather than silently generating one with blank fields. The **Staff Service Certificate** branches on `StaffMember.resignation`: present → "employed ... from {joiningDate} to {lastWorkingDate}"; absent → "employed since {joiningDate}, and continues to be employed here" — verified live for both branches (James Carter, active, correctly got the continuing-employment text; Geeta Naik, resigned, correctly got the dated employment-period text). Every issued certificate is a frozen snapshot (`IssuedCertificate.bodyLines`/`meta` captured at generation time into `localStorage`, never recomputed from the live student/staff record afterward), the same immutable-record discipline as Accounting's posted journal entries and Payroll's payslips — editing a student's or staff member's profile later does not retroactively alter a certificate already issued to them. Certificate numbers are sequential per type (`BON-2026-0001`, `SVC-2026-0002`, etc., tracked via `nextCertificateNumber(type)`), except Transfer Certificates which use the real `transferCertificateNumber` as noted above. **Issued Certificates** tab is a type-filterable log with view/print (`CertificateView`, print-style dialog mirroring Fees' `ReceiptView`/Payroll's `PayslipView`) and delete. Full generate-for-each-of-six-types cycle verified live in-browser (including the transfer-record-missing error path and both staff-service branches), nav-gating confirmed (teacher role sees no "Certificates" section; admin sees it under its own new nav section). Route: `/certificates`, its own new "Certificates" nav section, gated by a new `certificates` permission added to `ADMIN_ONLY_MODULES`.

22. **Health & Medical** (`src/features/health/`) — the fifth Phase B sub-module (user's choice again). Per-student baseline medical info (blood group/allergies/conditions/medications/doctor) already existed on `Student.medical`, editable from the student's own profile (`students/components/profile/MedicalTab.tsx`) — this task's real scope was the genuinely missing school-wide clinic system built as a new standalone module, same "read the real record, don't duplicate it" discipline as Payroll/Certificates: **Health Records** is a read-only, searchable overview joining every active student's real `Student.medical` fields with this module's own derived stats (last checkup date, overdue-vaccination count, infirmary visits this year) — it explicitly does not duplicate an edit form, its toolbar says outright that blood group/allergies/conditions are edited from the student's own profile. **Health Checkups** logs periodic height/weight/vision/dental records; BMI is computed on the fly (`calculateBmi`/`bmiCategory` in `constants.ts`) rather than stored, using standard adult BMI bands as a documented simplification for real pediatric growth-percentile charts. **Vaccinations** tracks per-student due/administered doses with a computed (not stored) `due`/`overdue`/`completed` status derived from `dueDate` vs. `dateAdministered` vs. today, and a "Mark administered" action that stamps a real administered-date/staff without needing a second parallel record. **Infirmary Visits** logs sick-bay visits (symptoms, temperature, treatment, medicine, outcome, parent-notified). **Reports** aggregates allergy/condition counts, overdue/upcoming vaccinations, visit-outcome breakdown, and BMI distribution, all pure derivations with no separately stored report data (same convention as Inventory's and Accounting's reports tabs). Route: `/health`, its own new "Health" nav section, gated by a new `health` permission added to `ADMIN_ONLY_MODULES`.

23. **Visitor Management** (`src/features/visitors/`) — the sixth Phase B sub-module (user's choice again), and unlike Health, a genuinely standalone system with no pre-existing partial implementation elsewhere: Hostel's own `VisitorLog` (task 10) is scoped narrowly to family visiting boarding students and was deliberately left alone rather than merged into this — they solve different problems (a boarding house's visitor register vs. a whole-campus front-desk log) and forcing them into one model would have entangled two unrelated flows for no real benefit. **Visitor Log** is the front-desk check-in/out register: a sequential badge number (`VIS-0001`, via `nextBadgeNumber`), an ID-proof capture, and a polymorphic "here to see" host — a real student (`hostStudentId`), a real staff member (`hostStaffId`), or free-text "other" (`hostOtherLabel`, for a department/event/delivery with no single person to name) — resolved to a real record via the same read-only `listStudents()`/`listStaff()` join convention as every other module this session, never a second disconnected directory. **Pre-Approved Visits** are appointments scheduled ahead of time (`scheduled` → `arrived`/`cancelled`/`no-show`); a "Check in now" action on a scheduled entry calls `checkInFromPreApproval`, which builds a real Visitor Log entry from the appointment's own details (not a second copy the front desk re-types) and links the two records both ways (`PreApprovedVisit.visitorEntryId`, `VisitorEntry.preApprovalId`) — verified live end-to-end (checked in a scheduled visitor, confirmed it appeared in the Visitor Log with a real badge number and the appointment flipped to "Arrived"). **Watchlist** is a simple flagged-name list with a reason; entering a visitor's name during check-in triggers a live, non-blocking warning banner (`getWatchlistMatch`, queried directly off the name field) — deliberately advisory rather than an automatic block, since a real front desk needs to exercise judgment (e.g. a parent barred from a custody dispute might still need to be let in by an administrator's override) rather than have the system silently deny entry — verified live (typing a seeded watchlist name immediately surfaced the correct warning). **Reports** aggregates who's currently on premises, visits today/30 days, average visit duration, visits by purpose, and the most-visited hosts, all pure derivations over the log (same convention as every other module's Reports tab this session).
